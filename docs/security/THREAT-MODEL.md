# LocalNodes web3 threat model (SEC-01)

## Scope & method

- **Date:** 2026-11-04 (draft, plan 19-07 Task 1). Updated 2026-11-04 with the 19-07 Task 2 decisions, which the orchestrator proposed and Tom accepted on 2026-11-05 (D-17 carries his 2026-11-03 stamp). Reconciled with the as-built code, tests and releases on 2026-11-05 (plan 19-12 Task 1).
- **Components:** `siwe_login` (drupal.org; hardened in Phase 19 and released as `1.0.0-beta5`, tag `26e6539` on `460f5b8`, then `1.0.0-beta6`, tag `5825b3a` on `0b19b67`), `safe_smart_accounts` (drupal.org 1.0.x at `f5593a6`), `group_treasury` (drupal.org 1.0.x at `80ee45e`, with its `social_group_treasury` submodule), and the WaaP integration (`siwe_login_waap`, designed in 19-02, built in 19-09 and fixed after the 19-10 UAT on the local, unpushed clone branch `waap-connector` at `6e6b6b3`; the sandbox `waap_login` module is a finding only).
- **Method:** STRIDE per component. Each component section names all six categories; a category with no threat has a row saying "None identified" and why. Threat IDs (TM-NN) are defined once, by the table row whose first cell is the ID. A threat that spans two components is listed once, in the component that owns the mitigation, and referenced by ID elsewhere.
- **Bar:** OWASP ASVS Level 1, with V2 (authentication), V3 (sessions), V4 (access control), V5 (input validation), V6 (cryptography) and V14 (configuration and supply chain) applying.
- **Dispositions:** `mitigate` (a control exists, with evidence), `mitigate later` (no control yet; deferred and listed under Open items), `accept` (residual risk owned by Tom, stamped "Accepted by: Tom Cox, YYYY-MM-DD — reason"), `transfer` (a third party carries the risk).
- **Sources:** 19-RESEARCH.md (Critical Findings F1-F10, Threat Model Inputs, Security Domain); 19-DELTA-REVIEW.md (rows routed to the threat model); 19-WAAP-SPIKE.md; 19-APPKIT-SPIKE.md; [waap-uat.md](waap-uat.md); [siwe-release-gate.md](siwe-release-gate.md); [followups.md](followups.md); the 19-03 to 19-11 and 19-13 SUMMARYs; source read on 2026-11-04 in `repos/siwe_login` (1.0.x at `d1b06d7`), `repos/safe_smart_accounts` and `repos/group_treasury`, re-read on 2026-11-05 at siwe_login 1.0.x `ce007ff` (`0b19b67` plus a CHANGELOG commit) and `waap-connector` `6e6b6b3`.
- **Evidence status:** every test is cited with the result its plan's SUMMARY (or [followups.md](followups.md)) records; counts are per plan and later plans added tests. No evidence marker is left pending. ## Assets

| Asset | Where it lives | Why it matters |
|-------|----------------|----------------|
| Member Drupal accounts and sessions | Drupal `users`, session store | Taking one over means posting, group roles and treasury access as that member |
| Address-to-account binding | `field_ethereum_address` on the user | The login key (D-11): whoever controls the binding logs in as the account |
| Member emails | `users_field_data.mail` | Recovery channel and D-12 inbox proof; personal data |
| Pending nonces and onboarding hand-offs | PrivateTempStore (`key_value_expire`), session attributes | Freshness and stage of an in-progress login |
| Safe linkage and proposal records | `safe_account`, `safe_configuration`, `safe_transaction` entities | Drupal's mirror of each Safe: address, signers, threshold, proposals, collected signatures, executed status. Access checks read the signer list |
| Group-to-treasury link | `group_treasury` relationship on the group | Decides which Safe a group shows and who may propose |
| WaaP member key | WaaP TEE / 2PC (human.tech), never Drupal | Signs the member's SIWE messages; LocalNodes never holds it |
| Site private key | Drupal `private_key` state | HMACs for email verification and D-12 link URLs |
| RPC and CDN availability | Pocket portal, public RPCs, jsDelivr, esm.sh | Wording of contract-wallet rejections, ENS, and delivery of browser code |
| Release artifacts | drupal.org git tags and release nodes | Every site running these modules installs what is tagged |

## Trust boundaries

| Boundary | What crosses it | Notes |
|----------|-----------------|-------|
| Browser ↔ Drupal `/siwe/*` | Nonce requests, signed SIWE messages, onboarding forms | Public routes (`_access: "TRUE"`). Everything from the browser is untrusted until verified against the signed text |
| Browser ↔ Drupal Safe and treasury routes | Proposals, signatures, execution reports, deployment reports | Authenticated, CSRF header token on the JSON writes; payloads are client-asserted |
| Browser ↔ WaaP iframe origin (`staging.waap.xyz` / `waap.xyz`) | Login UI, OTP and social auth, signing requests | Outside SRI; the iframe also talks to `auth-server.azure-staging.silk-protector.com`, `eu-assets.i.posthog.com` and `vercel.live` (19-02) |
| Browser ↔ jsDelivr / esm.sh | ethers, WaaP SDK modules, web3onboard modules | Static jsDelivr files carry SRI; esm.sh dynamic imports can't |
| Browser ↔ Ethereum RPC (wallet / Safe SDK) | Safe deployment and execution transactions | Signed by the member's wallet; Drupal only hears about the result afterwards |
| Drupal ↔ Ethereum RPC | `eth_getCode` (SIWE-03 wording), ENS forward and reverse lookups | Pocket portal by default (`ETHEREUM_PROVIDER_URL` override); `RpcProviderManager` appends four hard-coded public fallbacks |
| Drupal ↔ Safe Transaction Service API | Safe info for treasury reconnect / accessibility checks | Safe{Wallet}'s hosted service |
| Drupal ↔ SMTP (Resend) | Verification and D-12 link emails, password-reset mail | Inbox proof depends on mail delivery |
| drupal.org packaging ↔ every site | Tagged releases of the three modules | A bad or stray tag reaches every site that updates |

## Entry points

Read from the routing files on 2026-11-04.

| Route | Path | Access |
|-------|------|--------|
| `siwe_login.nonce` | `/siwe/nonce` | `_access: "TRUE"`, `no_cache` |
| `siwe_login.verify` | `/siwe/verify` | `_access: "TRUE"`; JSON content type required (415 otherwise) |

The `safe_transaction` entity declares edit and delete link templates, but it has no route provider and the routing file defines no edit or delete route, so no edit form is reachable.

**group_treasury** (`group_treasury.routing.yml`; `TreasuryAccessControlHandler`)

| Route | Path | Access (group permission via `group_permission.checker`) |
|-------|------|-------------------------------------------------------|
| `group_treasury.treasury` | `/group/{group}/treasury` | `accessView`: `view group_treasury` |
| `group_treasury.create` | `/group/{group}/treasury/create` | `accessManage`: `manage group_treasury` |
| `group_treasury.reconnect` | `/group/{group}/treasury/reconnect` | `accessManage`: `manage group_treasury` |
| `group_treasury.propose_transaction` | `/group/{group}/treasury/propose` | `accessPropose`: `propose group_treasury transactions` |
| `group_treasury.transaction_view` | `/group/{group}/treasury/transaction/{safe_transaction}` | `accessTransaction`: `sign` or `execute group_treasury transactions`, and the transaction must belong to this group's Safe |

Signing and executing a group proposal go through the safe_smart_accounts JSON routes above, so they are gated by `transactionApiAccess`, not by the group permissions.

**WaaP integration:** no route of its own (D-07). The connector is JavaScript plus a library definition and settings. It requests `/siwe/nonce` and posts the WaaP-signed message to `/siwe/verify`, the same endpoints as the wallet button.
